# emocar

A face on the car that reacts to how it moves. ESP32-C3 Super Mini + L3G4200D (GY-50) gyro
+ SH1106 1.3" OLED on one I²C bus (SDA GPIO8 / SCL GPIO9 — see [wiring.md](wiring.md)).

| State | Emoji | Trigger (config.h) |
|---|---|---|
| NORMAL | 🙂 | default |
| FAST | 😮 | 3-axis vibration RMS > `FAST_ENTER_RMS` (rolling fast = shaking more; a hand shake also triggers it) |
| SPINNING | 😵‍💫 | \|gz\| > `SPIN_ENTER_DPS`, one sign, for `HOLD_MS` |

Priority SPINNING > FAST > NORMAL, with hysteresis (`*_EXIT_*`) and a `HOLD_MS` hold time.
Thresholds were measured on tinicar with the `../L3G4200D` telemetry sketch; retune there and copy.


## Animations

Each state plays `/anim<N>.qgif` from LittleFS; if the file is missing or invalid the
code-drawn placeholder face from `anim_data.h` (PROGMEM) is shown instead. Animations are
**uploaded over WiFi, not compiled in** — see [server/README.md](server/README.md):

```bash
cd ~/sang/esp32/emocar/server && go build -o emocar-server . && ./emocar-server
# join the "emocar" WiFi network, open http://localhost:8080, pick a GIF per state
```

The car stores only the three active animations; the GIF library stays on the PC.
Uploaded animations survive power cycles and firmware reflashes (LittleFS is its own
partition). File frames stream from flash 1 KB at a time, so size is bounded by the
partition (~1.5 MB), not RAM; ≤ 255 frames per animation.

`mkanim.py` (no args) only regenerates the placeholder `anim_data.h` now.

The player never blocks: a frame is drawn when its delay elapses, and the gyro FIFO (32 samples
= 160 ms at 200 Hz) rides out the ~25 ms an SH1106 frame takes on the bus. A state change
restarts the new animation at frame 0 immediately.

## Build / flash

Arduino IDE: board **ESP32C3 Dev Module**, **USB CDC On Boot: Enabled**, port `/dev/ttyACM0`,
library **U8g2** (olikraus). Or:

```bash
cd ~/sang/esp32
arduino-cli compile --fqbn esp32:esp32:esp32c3:CDCOnBoot=cdc emocar
arduino-cli upload  --fqbn esp32:esp32:esp32c3:CDCOnBoot=cdc -p /dev/ttyACM0 emocar
arduino-cli monitor -p /dev/ttyACM0 -c baudrate=115200
```

Boot sequence on the OLED: `emocar` splash (shows the WiFi SSID) → `CALIBRATING keep still`
(1.5 s, car must not move) → 🙂. `GYRO ERROR` means no ACK at 0x69 or wrong WHO_AM_I — see the
checklist in wiring.md. During a WiFi upload the OLED shows `UPDATING` for a second or two.

Serial (115200) prints one telemetry line per `PRINT_MS`
(`gx gy gz | rms pk | gz pk | roll ctx | sps | state`) and `>>> state = …` on every change.
Set `PRINT_MS 0` to silence it.

⚠️ The calibration window is where things go wrong silently: if the car is moving during
those 1.5 s the motion is averaged into the zero-rate bias, and every reading afterwards
carries the offset. A stuck state with a constant non-zero axis at rest is this, not a
sensor fault — reset with the car flat and still. (PLANS.md P4.1 is the fix.)

## Tests

`motion.*` is pure logic — no I2C, no display — so it runs on the host against a fake clock:

```bash
make -C test test        # compiles motion.cpp with a stub Arduino.h and asserts each scenario
```

Scenarios cover the four states and the floor/hand context bit: pushed on the floor must
not read as held, a pickup must reach HAPPY, a shake must reach DIZZY and leave a tail
proportional to the rotation, and a hand shake in yaw must not be mistaken for a spin.
The blind spot is the magnitudes — a scenario is only as honest as the numbers fed into
it, so thresholds still have to be confirmed on real hardware (PLANS.md P5).
